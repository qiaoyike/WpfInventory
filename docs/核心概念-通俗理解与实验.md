# 核心概念：通俗理解与动手实验

> 配套 `docs/知识点-代码对照.md` 使用。那份偏“定义和面试答案”，这份偏“真懂”。
> 每个概念走四步：**一句话人话 → 生活类比 → 项目里的位置 → 破坏实验**。
> 破坏实验的目的不是改坏代码，而是让你亲眼看到“没有它会发生什么”。做完记得改回来。

---

## 0. 使用说明

1. 先读“一句话人话”，能自己复述再往下。
2. 把生活类比讲给一个不懂编程的人听，讲得通说明你抓到了本质。
3. 打开对应代码，看谁创建谁、谁调用谁。
4. 按“破坏实验”改一小段，编译或运行观察现象，然后还原。

---

## 1. 依赖注入 DI

**一句话人话**：对象不自己 `new` 依赖，而是别人把依赖塞给它。

**生活类比**：厨师不自己种菜，也不管菜从哪来，有人按菜单把食材送进后厨。厨师只负责“用”。

**项目里的位置**：

- `src/WpfInventory.App/App.xaml.cs` 的 `ConfigureServices` 是“送菜的人”，集中登记谁提供什么。
- `src/WpfInventory.Application/DependencyInjection.cs` 和 `src/WpfInventory.Infrastructure/DependencyInjection.cs` 是各层自己的登记表。
- `CategoryViewModel` 构造函数只声明“我需要服务”，不 `new` 具体实现。

**破坏实验**：

1. 打开 `src/WpfInventory.App/App.xaml.cs`，找到 `ConfigureUiServices`。
2. 临时注释掉任意一行，例如 `services.AddScoped<CategoryViewModel>();`。
3. 编译并运行，进入分类页面时会报“Unable to resolve service for type ...”。
4. 现象说明：容器找不到注册，就无法把对象塞进来；对象不是自己创建的。
5. 还原注释。

---

## 2. 接口

**一句话人话**：接口是一份“合同”，只规定“必须提供哪些能力”，不规定“怎么实现”。

**生活类比**：插座标准。充电器只要符合插座接口，墙后是水电、火电还是电池都不影响使用。

**项目里的位置**：

- `src/WpfInventory.Domain/Repositories/IRepository.cs` 是合同。
- `src/WpfInventory.Infrastructure/Persistence/Repositories/Repository.cs` 是具体实现。
- `CategoryViewModel` 只知道接口，不知道实现是 EF Core 还是内存列表。

**破坏实验**：

1. 打开 `IRepository<TEntity>`，给接口临时加一个方法：`Task<int> CountAsync(...)`。
2. 编译：`Repository<TEntity>` 会报“没有实现接口成员”。
3. 现象说明：接口一旦改合同，所有实现方都必须跟着改，这就是约束力。
4. 删除该方法，还原。

---

## 3. 泛型与泛型约束

**一句话人话**：写一个“万能模具”，换不同的具体类型就能复用同一套逻辑。

**生活类比**：招聘条件“必须有身份证”，不管来的是销售、程序员还是司机，都能进同一个流程。约束就是“必须有身份证”。

**项目里的位置**：

- `src/WpfInventory.Infrastructure/Persistence/Repositories/Repository.cs`：

```csharp
public class Repository<TEntity> : IRepository<TEntity> where TEntity : BaseEntity
```

- `src/WpfInventory.Application/Services/Crud/CrudAppService.cs` 用四个泛型参数，把“查/增/改/删”复用给分类、仓库、供应商、客户。

**破坏实验**：

1. 打开 `Repository.cs`，临时删掉 `where TEntity : BaseEntity`。
2. 编译：`GetByIdAsync` 里的 `x.Id` 会报“TEntity 不包含 Id 的定义”。
3. 现象说明：没有约束，编译器不知道 `TEntity` 一定有 `Id`；有了约束，才能安全使用 `BaseEntity` 的成员。
4. 把约束加回来，还原。

---

## 4. async / await

**一句话人话**：让你“先去做别的事，等结果回来再继续”，而不是傻站着等。

**生活类比**：你点完餐回座位刷手机，服务员上菜了喊你继续吃。`await` 就是“菜好了再回来吃”。

**项目里的位置**：

- `src/WpfInventory.App/ViewModels/CrudViewModelBase.cs` 的 `LoadAsync`。
- `src/WpfInventory.App/ViewModels/ProductViewModel.cs` 的 `LoadAsync`。
- `src/WpfInventory.App/App.xaml.cs` 的 `async void OnStartup`。

**破坏实验**：

1. 找一段 ViewModel 的 `await _service.GetAllAsync()`，临时改成 `.Result`：

```csharp
var data = _service.GetAllAsync().Result;
```

2. 对比理解：`await` 是异步等待，不阻塞 UI 线程；`.Result` 是同步阻塞，UI 可能卡住。
3. 更直观的实验：临时加一句 `await Task.Delay(3000);`，运行后界面仍能拖动；再换成 `Task.Delay(3000).Wait();`，窗口会卡 3 秒。
4. 做完还原。

## 5. 模板方法模式

**一句话人话**：基类定好“流程骨架”，子类只填“具体细节”。

**生活类比**：汉堡制作流程固定为“面包→肉饼→菜→包装”，但不同门店的肉饼和酱料不同。流程在总部，细节在门店。

**项目里的位置**：

- `src/WpfInventory.App/ViewModels/CrudViewModelBase.cs` 固定了“加载、新增、保存、删除”的流程。
- 子类 `CategoryViewModel`、`WarehouseViewModel` 等实现 `BuildCreateRequest`、`LoadFromItem`、`ClearForm`、`GetId`。

**破坏实验**：

1. 打开 `src/WpfInventory.App/ViewModels/CategoryViewModel.cs`。
2. 临时删除一个抽象方法实现，例如 `BuildCreateRequest`。
3. 编译：会报“未实现继承的抽象成员”。
4. 现象说明：基类要求子类必须填空，流程控制权在基类。
5. 还原。

---

## 6. 仓储模式 Repository

**一句话人话**：给数据访问包一层“管理员”，上层只找管理员要数据，不直接碰数据库细节。

**生活类比**：你到仓库取货只找仓库管理员，不用自己懂货架编号、叉车路线。

**项目里的位置**：

- `src/WpfInventory.Domain/Repositories/IRepository.cs`：管理员的职责合同。
- `src/WpfInventory.Infrastructure/Persistence/Repositories/Repository.cs`：EF Core 版管理员。

**破坏实验**：

1. 打开 `Repository<TEntity>.GetAllAsync`。
2. 临时加一个过滤条件，例如只返回 `IsActive == true` 的记录。
3. 运行应用，所有使用该仓储的列表自动只显示启用记录。
4. 现象说明：查询逻辑集中在一处，上层不用改；如果散落在各 ViewModel 里，每个地方都要改。
5. 还原。

## 7. 工作单元 UnitOfWork

**一句话人话**：把多次写操作“打包成一次提交”，要么全成功，要么全回滚。

**生活类比**：转账时“扣你的钱”和“加对方的钱”必须一起生效，不能只做一半。

**项目里的位置**：

- `src/WpfInventory.Application/Abstractions/Persistence/IUnitOfWork.cs`：打包合同。
- `src/WpfInventory.Infrastructure/Persistence/EfUnitOfWork.cs`：具体打包逻辑。

**破坏实验**：

1. 直接看现有测试 `tests/WpfInventory.Infrastructure.Tests/EfUnitOfWorkTests.cs`。
2. 它验证了：操作成功会提交；操作抛异常会回滚。
3. 运行 `dotnet test`，或只读该文件理解“提交/回滚”两条路径。
4. 想手动实验：在事务 `action` 里故意 `throw`，看数据库没有残留数据。

---

## 8. DTO

**一句话人话**：界面只拿它需要的“精简版数据”，不直接拿数据库实体。

**生活类比**：办业务只给你一张“业务回执单”，而不是把整本档案原件给你。

**项目里的位置**：

- 实体：`src/WpfInventory.Domain/Entities/Product.cs`，含 `Category` 导航属性等完整信息。
- DTO：`src/WpfInventory.Application/Dtos/Products/ProductDto.cs`，只放界面需要的字段。
- 映射：`src/WpfInventory.Application/Mapping/ProductMappingProfile.cs`。

**破坏实验**：

1. 试着想象让 `DataGrid` 直接绑定 `Product` 实体：会看到 `Category` 对象、外键等一堆不该出现的东西，还可能序列化循环引用。
2. 打开 `ProductDto`，看它比 `Product` 少了导航属性，更贴合页面。
3. 修改 `ProductMappingProfile` 中一个字段映射，看界面显示变化，理解“实体 → DTO”的转换。
4. 实验后还原。

---

## 9. WPF 数据绑定

**一句话人话**：界面上的控件和 ViewModel 属性之间拉一条“自动同步的线”。

**生活类比**：仪表盘指针连着传感器，传感器数值变，指针自动动。

**项目里的位置**：

- `src/WpfInventory.App/Views/CategoryView.xaml` 的 `Text="{Binding Name}"`。
- 数据上下文由主窗口切页时设置，见 `MainWindowViewModel` 和 `MainWindow.xaml` 的 `ContentControl`。

**破坏实验**：

1. 打开 `CategoryView.xaml`。
2. 把某处 `{Binding Name}` 临时改成 `{Binding Name2}`。
3. 运行，观察 Visual Studio 输出窗口出现绑定错误，文本框不再显示分类名。
4. 现象说明：绑定靠“路径 + DataContext”找属性，路径错就断线。
5. 还原。

---

## 10. ICommand / RelayCommand

**一句话人话**：把“按钮点击后做什么”包装成对象，界面只绑定命令名，不写点击事件代码。

**生活类比**：电梯按钮连的是统一的调度命令，按哪个钮都走同一套执行机制。

**项目里的位置**：

- `CrudViewModelBase.cs` 中 `[RelayCommand] private async Task SaveAsync()` 自动生成 `SaveCommand`。
- `CategoryView.xaml` 中 `Command="{Binding SaveCommand}"`。

**破坏实验**：

1. 打开 `CategoryView.xaml`。
2. 把保存按钮的 `Command="{Binding SaveCommand}"` 临时改成 `Command="{Binding SaveCommandX}"`。
3. 运行后点保存，按钮没有反应。
4. 现象说明：命令是一个可绑定的对象，名字不对就找不到执行入口。
5. 还原，或把 `[RelayCommand]` 临时去掉，看 `SaveCommand` 不再生成。

## 学完一个概念的验收标准

不用背定义，只问自己三句：

1. 我能用一句人话讲清楚它吗？
2. 我能说一个贴近生活的类比，并指出类比不严谨的地方吗？
3. 我能把项目里某处代码改坏，并预判会出现什么现象吗？

三句都过，才算真正理解。
